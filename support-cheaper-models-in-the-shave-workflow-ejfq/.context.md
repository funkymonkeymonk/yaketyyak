# Support cheaper models in the shave workflow

## Problem

Pi's tool-calling format is only compatible with a subset of models. Testing
against the LiteLLM gateway showed:

- claude-sonnet-4-6 ✓
- claude-haiku-4-5 ✓
- claude-opus-4-5 ✓
- moonshotai.kimi-k2.5 ✗ (malformed_model_output — doesn't support tool params)

Currently DefaultPiModel is hardcoded to claude-sonnet-4-6. We want to be
able to use cheaper models (e.g. haiku for simple yaks, or non-Claude models
if they gain Pi compatibility) without changing code.

## Goal

Make model selection smarter and cheaper without sacrificing reliability.

## Options to explore

1. **Task-based model selection**: simple/mechanical yaks (docs, config,
   renaming) use haiku; complex yaks (new features, refactors) use sonnet.
   Could be declared in the yak context with a `model:` field or tag.

2. **Compatibility testing harness**: a small test suite that checks a model
   works with Pi tool-calling before it's used in production. Run against
   the LiteLLM gateway to build a known-good model list.

3. **Fallback chain**: try cheaper model first, fall back to sonnet on
   malformed_model_output. Pi already surfaces this as a distinct error.

4. **Non-Claude models**: investigate which non-Claude models in the gateway
   support Pi's tool-calling (parallel function calling, structured output).
   Candidates: gpt-5.x variants, Gemini models.

## Current model list in gateway (as of 2026-05-27)

Compatible: claude-sonnet-4-6, claude-haiku-4-5-20251001, claude-opus-4-5-20251101
Incompatible: moonshotai.kimi-k2.5, moonshot.kimi-k2-thinking

## Acceptance criteria

- At least one cheaper model (haiku or equivalent) is usable for simple yaks
- Incompatible models fail fast with a clear error, not a wasted agent run
- DefaultPiModel remains a safe fallback
