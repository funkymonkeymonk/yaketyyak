# Barber Workflow

**Status**: Parked — needs more design before implementation.

## Purpose

The Barber is a planning and refinement agent. It bridges vague tickets/ideas
and well-specified yaks that are ready to shave autonomously.

## Responsibilities

1. **Refinement**: Take a vague requirement and produce a tight `.context.md`
   spec with clear scope, acceptance criteria, and constraints. Uses direct LLM
   calls (structured reasoning on text, not code writing).

2. **Dependency management**: Detect when yak B depends on yak A. Block
   promotion to `@g2g` until prerequisites are done.

3. **Risk/complexity check**: Flag yaks that are too large or ambiguous for
   autonomous shaving. Require human review before `@g2g`.

4. **Promotion**: Mark yaks `@g2g` automatically when criteria are met, or
   surface them for human confirmation.

## Open questions to resolve before implementing

- How does the Barber receive input? (Jira webhook, manual `yyx refine`, TUI action?)
- What does "dependency" look like in the yak data model? (tag? field? parent/child?)
- Should the Barber be always-on (Temporal workflow) or invoked on demand?
- How does it interact with the `yx` CLI vs. directly with the yak store?

## Not in scope here

The Barber does NOT implement yaks. That is `YakWorkflow`'s job.
