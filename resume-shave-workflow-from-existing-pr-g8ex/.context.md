## Goal

Enable resuming or restarting a shave workflow for PRs that already exist on GitHub (e.g. PR #3, #4, #6) by providing review feedback on them. Currently, `YakWorkflow` always starts fresh (claim → workspace → agent → create PR). There is no path to reconnect a running or dead workflow to an existing PR.

## Problem

PRs #3, #4, and #6 were opened by previous shave runs. Those workflow instances are either:
- Timed out / terminated
- Still running but stuck

When someone leaves a review comment on GitHub, there is no mechanism to route that feedback back to the workflow. The `WatchPRState` activity polls for review events, but it only runs within an active workflow that already holds a reference to the PR number.

## Design considerations

Two complementary approaches are likely needed:

### 1. A "resume" trigger / signal

Add a new signal or a new `yy` subcommand (e.g. `yy resume <yak-name> --pr <number>`) that:
- Starts a new YakWorkflow execution (or re-uses an existing one via `signal-with-start`)
- Skips the claim/workspace/agent/create-PR steps
- Jumps straight to `waiting-for-merge` with the known PR number and repo URL

This likely requires:
- A new `ResumeConfig` or discriminated union in `WorkflowConfig` to express "we already have a PR at #N"
- The workflow to branch early based on whether a PR already exists
- Possibly a `signal-with-start` approach so a single workflow ID per yak is canonical

### 2. GitHub webhook → Temporal signal bridge

Right now the worker polls via `WatchPRState`. For stale workflows there is nobody polling. A better long-term architecture:
- GitHub webhook (or GitHub Actions `pull_request_review` event) fires when a review is submitted
- A lightweight handler (could be `yy cisignal` or a new subcommand) receives the event, looks up the workflow ID by PR number or yak name, and sends a Temporal signal
- The workflow wakes up and processes the feedback

This is related to the `cisignal` command already present in the codebase.

## Immediate need

Unblock PR #3 (yak-templates), PR #4 (session-discipline--triage-wrap-), PR #6 (activity-timeline-spans) by being able to post review comments and have the workflow pick them up.

## Open questions

- Should resume start a brand-new workflow run or signal an existing one?
- Can `WatchPRState` be made robust enough to re-attach to a PR it hasn't seen before?
- Do we need to persist PR number in yak fields so resume can be automatic?
