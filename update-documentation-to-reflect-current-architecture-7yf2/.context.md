# Update documentation to reflect current architecture

## Goal

Bring all docs into sync with the actual codebase. An agent reading the docs
should get an accurate picture of how yaketyyak works today.

## Current architecture (source of truth)

**Binaries:**
- `yyx` — TUI (read-only yak browser, no workflow dispatch)
- `yyx-worker` — Temporal worker process, built to `dist/`

**Workflow:**
- `YakWorkflow` — one per yak, ID = `yyx-yak-<sanitized-yak-name>`
  - Phases: init → claiming → init-workspace → implementing → creating-pr → waiting-for-merge → done
  - Signal: `wont-do` (cancels and releases the yak)
  - Query: `yak_status` → returns `YakWorkflowState{YakName, Phase, Workspace, PRURL, PRNumber}`

**Activities:** YakClaim, YakRelease, YakMarkDone, WritePRToYak, InitWorkspace,
CleanupWorkspace, RunAgent (Pi subprocess), CreateDraftPR, WatchPRMerged

**Types:** PiConfig, YakWorkflowState, PRResult

**CLI:**
- `yyx shave <yak-name>` — starts a YakWorkflow
  - Flags: --pi-provider, --pi-model, --pi-tools, --pi-skill, --repo-root
- `yyx` (no args) — launches TUI

**Key design decisions:**
- Pi coding agent (`pi --print --no-session`) implements the yak, not raw LLM calls
- Human drives PR: workflow creates a draft PR, human reviews/approves/merges
- Workflow observes merge via polling (`gh pr view`), does not auto-merge
- `BarberWorkflow` is planned but not yet built
